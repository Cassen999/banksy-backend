# BanksyDB — Implementation Plan

## Design Decisions

### Why UUID over sequential integer IDs
Sequential IDs (`1, 2, 3...`) are guessable. A UUID like `a3f8c2d1-...` cannot be enumerated.
For a banking app this matters — you don't want someone to be able to guess another user's ID.

### Why no password field
With OAuth, Google verifies the user's identity. You never receive or store a password.
This eliminates an entire class of security vulnerabilities.

### Why SharedAccount is replaced by a junction table
Your original design had arrays of user IDs and bank IDs inside a SharedAccount row.
SQL cannot enforce foreign key constraints on array contents, meaning the database cannot
guarantee those IDs actually exist. The `user_plaid_items` junction table achieves the same
goal — linking multiple users to the same bank connection — with proper constraints, indexes,
and safe cascade deletes.

### Why transaction and balance data is never stored
Plaid serves live data. Storing it would require keeping it in sync, encrypted at rest, and
subject to data breach risk. Fetching it live on each request is simpler and safer.

## Encryption Strategy

Application-level AES-256-GCM encryption with the key stored as an environment variable.

```
Environment variable:  ENCRYPTION_KEY=<32-byte random key>

Stored in DB:          access_token_enc = "AES256:iv:ciphertext"
In memory (briefly):   access_token = "access-sandbox-abc123..."
```

If someone dumps the database, access tokens are unreadable without the key. The environment
variable is the single point of trust — store it as a secret in your deployment platform's
dashboard, never in source code.

## Libraries

| Purpose | Library | Why |
|---|---|---|
| OAuth 2.0 | `spring-security-oauth2-client` | Official Spring, handles Google flow |
| DB migrations | Flyway | Version-controls your schema — critical for not losing data on redeploy |
| Encryption | Java AES-GCM (built-in JCE) | No extra dependency, AES-256-GCM is the standard |
| ORM | Spring Data JPA | Likely already in stack |

## Implementation Phases

1. **Schema** — Write Flyway migrations for all 5 tables
2. **Encryption service** — AES-256-GCM encrypt/decrypt utility for `access_token`
3. **OAuth** — Replace current auth with Spring Security + Google OAuth; populate `users` and `oauth_identities`
4. **Update Plaid integration** — Wire existing Plaid code to store data in new tables with encrypted tokens
5. **Shared access endpoint** — Allow a user to share a `plaid_item` with another user by email
