- Runtime: Java 21, Spring Boot 3, Maven
- Group: `org.example`, artifact: `banksy`
- Database: PostgreSQL via Spring Data JPA, Flyway for migrations
- Auth: Google OAuth2, session cookie (JSESSIONID)

## SECTION 3 — LAYER RULES

### `controller`
- MAY call one service and/or `UserRepository` (for user resolution only).
- MUST call `SecurityUtils.resolveUser()` to obtain the current user; pass `userId` (UUID) to services.
- MUST NOT call repositories other than `UserRepository`.
- MUST NOT contain business logic — any `if` not about HTTP status codes belongs in a service.
- All endpoints MUST be under `/api/**`.

### `service`
- MAY call any repository.
- MUST access Plaid via `PlaidEnvironmentService.getClient()` — MUST NOT inject `PlaidApi` directly.
- MAY call other services (e.g. `EncryptionService`).
- MUST NOT handle HTTP concerns (`HttpServletRequest`, `ResponseEntity`, status codes).
- MUST NOT resolve the current user from an `OAuth2User` principal — receive `userId` (UUID) from the controller.

### `repository`
- MAY only interact with its own entity type and eagerly fetched associations declared in the entity.
- MUST NOT call other repositories.
- MUST NOT contain business logic.
- New repositories MUST extend `JpaRepository<Entity, UUID>` or `JpaRepository<Entity, Integer>` for single-row config tables.

### `entity`
- MUST NOT contain business logic. `@PrePersist` / `@PreUpdate` lifecycle methods for timestamps are the only exception.
- Primary keys MUST be `UUID` generated by the database (`GenerationType.UUID`), except single-row config tables which use `SERIAL INTEGER` (`GenerationType.IDENTITY`).
- Every new entity MUST have a corresponding Flyway migration in `src/main/resources/db/migration/`.

### `model`
- MUST be Java `record`s (not classes).
- MUST NOT carry JPA annotations or be used as database entities.
- MUST NOT contain business logic.

## SECTION 6 — WHAT NOT TO DO

- ❌ Do not inject `PlaidApi` directly — always call `PlaidEnvironmentService.getClient()`
- ❌ Do not resolve the authenticated user inside a service — controllers call `SecurityUtils.resolveUser()` and pass `userId` (UUID) to services
- ❌ Do not call repositories directly from controllers (except `UserRepository` for user resolution)
- ❌ Do not put business logic in controllers — if you are writing an `if` statement that is not about an HTTP status code, it belongs in a service
- ❌ Do not add JPA annotations to model records — models are DTOs, not entities
- ❌ Do not hardcode credentials — all secrets come from environment variables
- ❌ Do not use React Context for server state on the frontend (tried, rolled back)
- ❌ Do not modify an already-applied Flyway migration — add a new one instead
- ❌ Do not use a global `@ControllerAdvice` for exception mapping — there is none in this codebase; services throw typed exceptions and each controller catches them directly in its own try/catch blocks
- ❌ Do not use `IllegalArgumentException` for any purpose other than signaling a bad or invalid input from the caller (maps to `400`); thrown by services when a referenced resource does not exist or an operation is invalid (e.g. item not found, email not found)
- ❌ Do not use `SecurityException` for any purpose other than signaling that the calling user is not authorized for the requested resource (maps to `403`); thrown by services when the user is not the owner or not linked to the target item
- ❌ Do not use `NoSuchElementException` for any purpose other than signaling that a requested entity was not found in the database (maps to `404`); use this — not `IllegalArgumentException` — when a missing record should return 404 rather than 400
- ❌ Do not use `RuntimeException` or `IOException` to signal business-rule violations — these are reserved for Plaid API failures and infrastructure errors and map to `500`
- ❌ Do not return `null` or an empty result from a service to signal a missing resource or authorization failure — throw the appropriate typed exception (`IllegalArgumentException`, `SecurityException`, or `NoSuchElementException`) so the controller can map it to the correct HTTP status

## SECTION 9 — HOOK SYSTEM

**`audit_before_code.py`** (PreToolUse / Bash)
- Fires when any code-related keyword is detected in a prompt.
- Injects `ARCHITECTURE.md` and current schema from Flyway migrations.
- Hard blocks if `plans/.active-feature` is missing or points to a folder without all three plan documents.

**`enforce_during_implementation.py`** (PreToolUse / file writes)
- Fires on every file write to `src/main/java/`.
- Hard blocks if the corresponding test file does not exist.
- Hard blocks if plans are incomplete or user approval is absent.
- Warns when modifying an existing file without touching its tests.

**`definition_of_done.py`** (PostToolUse / Bash)
- Fires after implementation work.
- Runs `mvn test` and `mvn jacoco:report`.
- Hard blocks if: any test fails, line coverage < 90%, branch coverage < 90%, new/modified components are not documented in `ARCHITECTURE.md`, or `ENDPOINTS.md` / `SCHEMA.md` are stale relative to changed files.
- Writes `TEST_REPORT.md` and `FIX_PLAN.md` to `testing/<feature-name>/`.

**Coverage exclusions** (not counted toward 90%): `Main`, `*Config`, `*Configuration`, `*Exception`, `entity/*` package.

## SECTION 10 — ACTIVE FEATURE TRACKING

`plans/.active-feature` must always contain the exact name of the feature currently being worked on. This name must match an existing folder under `plans/`.

**When starting a new feature:**
1. Choose a kebab-case feature name (e.g. `budget-tracking`)
2. Write that name to `plans/.active-feature`
3. Create `plans/<feature-name>/IMPLEMENTATION_PLAN.md`
4. Create `plans/<feature-name>/TEST_PLAN.md`
5. Create `plans/<feature-name>/DIAGRAMS.md`
6. Present all three to the user and wait for explicit approval
7. Do not write any implementation code until approval is received

**Approval keywords:** approved, approve, lgtm, looks good, go ahead, proceed, ship it, good to go, confirmed, confirm, happy with, commence, start implementation, begin implementation, start coding, begin coding
